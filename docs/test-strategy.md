# Test Strategy

The sample system is intentionally tiny; the testing model is not. Every layer below exists
to answer one specific question as cheaply as possible, and to stay out of the layers above it.

## Layer map

| Layer | Tool | Question it answers | Runs in | Typical runtime |
|---|---|---|---|---|
| Unit | Vitest | Is the checkout validation logic correct at every boundary? | Node, no I/O | milliseconds |
| API (in-process) | Vitest + Supertest | Does the HTTP layer route, parse, validate and fail correctly? | Node, no network | milliseconds |
| Contract | Pact | Can the UI client and the User API evolve independently without breaking each other? | Node, mock server | seconds |
| Integration | Testcontainers + PostgreSQL | Does persistence behave correctly against the real database engine? | Docker | ~20 s (container start) |
| Browser E2E | Playwright | Can a customer complete the critical journey and understand failures? | Chromium | seconds |
| Accessibility | axe-core + Playwright | Are there detectable WCAG A/AA defects, including after interaction? | Chromium | seconds |
| Performance | k6 (protocol + browser) | Does the service meet latency/error budgets under load? | k6 runtime | scheduled |
| AI evaluation | Promptfoo | Does a probabilistic feature still meet deterministic safety/format rules? | model API | on demand |
| Observability | OpenTelemetry | When something fails, can we see *where* without re-running? | runtime | always-on |

## Placement rules

1. **Push tests down.** A rule that can be proven with a pure function test is not proven in the browser.
   Example: quantity boundaries live in `tests/unit`, not in a Playwright spec.
2. **Browser tests cover journeys, not permutations.** The E2E suite has one happy path and two
   user-visible failure paths. Every API status code is covered in `tests/api` instead.
3. **Verify UI claims through the API.** The E2E checkout test reads the order id from the page and then
   fetches the order server-side. The assertion is on system state, not on text alone.
4. **Real infrastructure only where semantics matter.** The in-memory repository is enough for routing and
   validation. PostgreSQL is used to prove constraints (`CHECK`, primary key) that a mock would happily ignore.
5. **Contracts before environments.** Pact catches shape drift between consumer and provider without an
   integrated environment. It does not replace the provider's own API tests.
6. **Deterministic CI.** Anything probabilistic (AI evals) or infrastructure-sensitive (performance)
   runs on demand or on a schedule, never as a per-commit gate.

## Flakiness policy

- Locators are role-based (`getByRole`) and assertions are web-first (`expect(locator).toHaveText`).
  No `waitForTimeout`, no CSS-path selectors.
- Retries are enabled in CI only (`retries: 2`) and a trace is captured on the first retry so a flaky
  test produces evidence instead of a re-run.
- A test that needs a retry to pass is treated as a defect in the test or the app, not as noise.

## What is deliberately *not* here

- **Visual regression baselines.** Screenshot baselines are OS- and font-dependent; keeping them green across
  macOS and Ubuntu adds maintenance without adding signal for this app. See ADR-0005.
- **Committed Pact files.** Pacts are generated by the consumer test in CI and verified in the same run.
  In a multi-repo setup they would be published to a Pact Broker. See ADR-0003.
- **Cross-browser matrix.** One Chromium project keeps CI fast; adding Firefox/WebKit is a one-line
  change in `playwright.config.ts` when the risk profile justifies it.
